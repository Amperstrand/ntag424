# NTAG 424 DNA — Secure Dynamic Messaging Notes

This note summarizes the crypto routines needed for Secure Dynamic Messaging
(SDM) from `NT4H2421Gx` rev. 3.0, section `9.3` (pages 34-43).

It is intended as an implementation guide for `ntag424-core`, not as a full
feature-spec walkthrough.

## Scope

SDM is for **not authenticated** reads of a `StandardData` file. It provides:

- mirrored `PICCData` containing `UID` and/or `SDMReadCtr`
- optional encrypted mirroring of file bytes (`SDMENCFileData`)
- mandatory MAC over the dynamic file view (`SDMMAC`) when `SDMFileRead` is
  configured to an application key

This is separate from post-auth secure messaging:

- authenticated session crypto lives in `crypto::suite`
- SDM uses file-configured SDM keys and the read counter instead

## Byte Order

The datasheet is strict about `SDMReadCtr` representation:

- `SDMReadCtr` is a 24-bit unsigned integer
- in crypto calculations and binary interface form: `LSB` first
- in mirrored ASCII form: `MSB` first

Implication:

- the 3-byte binary counter value used for KDFs and encryption counters should
  be the LSB-first encoding from the card/protocol
- the human-visible mirrored ASCII value is the hex string of the numeric value
  in normal most-significant-byte-first order

## Counter Semantics

`SDMReadCtr` behavior from `§9.3.1`:

- reset to `000000h` when SDM is enabled by `ChangeFileSettings`
- incremented by `1` before calculating the response for the **first**
  successful `ReadData` or `ISOReadBinary` in not-authenticated state
- repeated reads of the same file by the same command type reuse the current
  counter value
- switching command type or receiving a different command causes the next read
  to increment again
- command chaining counts as one command
- authenticated reads do **not** increment `SDMReadCtr`

Verifier-side minimum rule from the datasheet:

- track `SDMReadCtr` per tag and reject replays or out-of-order values

## Counter Limit

`SDMReadCtrLimit` from `§9.3.2`:

- optional 3-byte unsigned integer, `LSB` first on the interface
- configured via `ChangeFileSettings`; retrievable via `GetFileSettings`
- once `SDMReadCtr == SDMReadCtrLimit`, not-authenticated reads of the file
  fail with an error
- disabling the limit is equivalent to the maximum value `FFFFFFh`
- authenticated reads still work even past the limit (regular secure messaging)

## PICCData

`PICCData` mirrors metadata:

- `UID`
- `SDMReadCtr`

Plain mirroring (`SDMMetaRead = Eh`):

- output is ASCII encoded
- `UID` length with 7-byte UID: `14` bytes
- `SDMReadCtr` length: `6` bytes

Encrypted mirroring (`SDMMetaRead = 0h..4h`):

- plaintext format:

```text
PICCDataPlain = PICCDataTag [|| UID] [|| SDMReadCtr] || RandomPadding
```

- `PICCDataTag`:
  - bit 7: UID mirrored
  - bit 6: SDMReadCtr mirrored
  - bits 5-4: RFU = `00`
  - bits 3-0: UID length
    - `7h` when a 7-byte UID is mirrored
    - `0h` (RFU) when UID mirroring is disabled

Random padding rules from `§9.3.4`:

- pad the plaintext to exactly one 16-byte AES block (not a multiple) —
  spec: "RandomPadding being a random byte string generated by the PICC to
  make the input 16 bytes long"
- with a 7-byte UID and both fields mirrored that is `1 + 7 + 3 = 11` bytes
  of content plus `5` random bytes; with UID/counter absent the tag byte is
  padded with `15` random bytes
- generated freshly for the first qualifying read command
- reused for subsequent reads of the same file / same command type
- regenerated when another command intervenes or the command type changes

## PICCData Encryption

### AES mode

From `§9.3.4.1`:

```text
PICCData = AES-CBC-ENC(
    key = SDMMetaReadKey,
    iv  = 00...00,
    pt  = PICCDataTag [|| UID] [|| SDMReadCtr] || RandomPadding
)
```

Notes:

- zero IV, not the secure-messaging `(TI, CmdCtr)` IV scheme
- output is mirrored ASCII-encoded in the file, so the placeholder length is
  doubled

### LRP mode

From `§9.3.4.2`:

```text
SDMMetaReadSPT = generatePlaintexts(4; SDMMetaReadKey)
{SDMMetaReadUpdateKey} = generateUpdatedKeys(1; SDMMetaReadKey)

PICCData = PICCRand || ELRP(
    key     = SDMMetaReadKey,
    counter = PICCRand,
    pt      = PICCDataTag [|| UID] [|| SDMReadCtr] || RandomPadding
)
```

Notes:

- `PICCRand` is 8 random bytes, generated by the PICC
- this uses LRICB with the 8-byte random as counter input
- `RandomPadding` is applied like for AES mode, so the LRICB plaintext is
  one 16-byte block
- required mirrored placeholder length is `48` ASCII bytes
  (`8` bytes `PICCRand` + `16` bytes ciphertext, ASCII-doubled)
- wire format differs from AES: `PICCRand` is prefixed in plain before the
  ciphertext

## SDMENCFileData

`SDMENCFileData` is optional encrypted mirroring of part of the file.

Important rules from `§9.3.5` and `§9.3.6`:

- only applies in not-authenticated state
- input plaintext is always binary
- output ciphertext is mirrored as ASCII
- `SDMENCLength` is an ASCII placeholder length
- only the first half of the placeholder stores plaintext; the second half is
  ignored when producing the SDM read response
- for ASCII mode, `SDMENCLength` must be a multiple of `32` bytes
- the actual encrypted plaintext length is `SDMENCLength / 2`
- no padding is applied; input length is guaranteed by configuration to be a
  multiple of 16 bytes

### AES mode

From `§9.3.6.1`:

```text
IV = AES-ECB-ENC(
    key = SesSDMFileReadENCKey,
    pt  = SDMReadCtr || 00 00 00 00 00 00 00 00 00 00 00 00 00
)

SDMENCFileData = AES-CBC-ENC(
    key = SesSDMFileReadENCKey,
    iv  = IV,
    pt  = StaticFileData[SDMENCOffset .. SDMENCOffset + SDMENCLength/2 - 1]
)
```

Notes:

- `SDMReadCtr` is `LSB` first in the IV input
- this is the SDM analogue of authenticated AES secure messaging, but keyed by
  `SesSDMFileReadENCKey`

### LRP mode

From `§9.3.6.2`:

```text
counter = SDMReadCtr || 00 00 00

SDMENCFileData = ELRP(
    key     = SesSDMFileReadENCKey,
    counter = counter,
    pt      = StaticFileData[SDMENCOffset .. SDMENCOffset + SDMENCLength/2 - 1]
)
```

Notes:

- the counter is 6 bytes total
- the first 3 bytes are the `LSB`-first `SDMReadCtr`
- after concatenation the 6 bytes are treated as one unsigned integer for LRICB

## SDMMAC

When `SDMFileRead` is configured to an application key, MACing is mandatory.

From `§9.3.7` and `§9.3.8`:

```text
SDMMAC = MACt(Key; DynamicFileData[SDMMACInputOffset .. SDMMACOffset - 1])
```

Where `DynamicFileData` means:

- the file content as presented on the RF interface
- placeholders already replaced by dynamic output

Placement constraints from `§9.3.7`:

- `SDMMAC` is always mirrored within the file (NT4H2421Gx supports ASCII
  encoding only)
- raw MAC is `8` bytes, mirrored as `16` ASCII bytes
- if `SDMENCFileData` is mirrored, `SDMMACOffset ≥ SDMENCOffset + SDMENCLength`
- `SDMMACInputOffset ≤ SDMMACOffset` and must cover the full
  `SDMENCFileData` range so the MAC is computed over the encrypted bytes
- `SDMMACOffset + SDMMACLength ≤ file size`

### AES mode

```text
SDMMAC = MACt(SesSDMFileReadMACKey; DynamicFileData[...])
```

Use the same truncation as AES secure messaging:

- keep bytes `1,3,5,7,9,11,13,15` of the 16-byte CMAC result

### LRP mode

```text
SDMMAC = MACtLRP(SesSDMFileReadMACKey; DynamicFileData[...])
```

Use the same truncation as LRP secure messaging:

- identical even-indexed-byte selection as above

## SDM Session Key Derivation

The file access right `SDMFileRead` determines the base key used for SDM file
encryption and MAC derivation.

### AES mode (`§9.3.9.1`)

Session vectors:

```text
SV1 = C3 3C 00 01 00 80 || UID || SDMReadCtr
SV2 = 3C C3 00 01 00 80 [|| UID] [|| SDMReadCtr] [|| ZeroPadding]
```

Rules:

- `UID` and `SDMReadCtr` are included in `SV2` only if they are mirrored
- for encrypted file data they are effectively mandatory
- pad `SV2` with zero bytes up to a multiple of 16 bytes
- with a 7-byte UID and both fields mirrored `SV2` is already `6 + 7 + 3 = 16`
  bytes, so no padding is added

Derived keys:

```text
SesSDMFileReadENCKey = CMAC(SDMFileReadKey; SV1)
SesSDMFileReadMACKey = CMAC(SDMFileReadKey; SV2)
```

### LRP mode (`§9.3.9.2`)

Session vector:

```text
SV = 00 01 00 80 [|| UID] [|| SDMReadCtr] [|| ZeroPadding] || 1E E1
```

Derived material:

```text
SDMFileReadSPT          = generatePlaintexts(4; SDMFileReadKey)
{SDMFileReadUpdateKey}  = generateUpdatedKeys(1; SDMFileReadKey)

SesSDMFileReadMasterKey = MACLRP(SDMFileReadKey; SV)
SesSDMFileReadSPT       = generatePlaintexts(4; SesSDMFileReadMasterKey)
{SesSDMFileReadMACUpdateKey; SesSDMFileReadENCUpdateKey} =
    generateUpdatedKeys(2; SesSDMFileReadMasterKey)
```

The first two lines build the LRP representation of `SDMFileReadKey` needed
to invoke `MACLRP` on `SV`.

The effective keys are:

- `SesSDMFileReadMACKey = (SesSDMFileReadSPT, SesSDMFileReadMACUpdateKey)`
- `SesSDMFileReadENCKey = (SesSDMFileReadSPT, SesSDMFileReadENCUpdateKey)`

This matches the way authenticated LRP session keys are represented in
`crypto::suite`.

## Implementation Mapping For This Repo

Recommended split:

- `crypto::suite`
  - authenticated secure messaging only
- `crypto::sdm`
  - SDM-specific key derivation and read-side crypto

Suggested pure-crypto routines:

- AES:
  - `derive_sdm_keys_aes`
  - `encrypt_picc_data_aes`
  - `decrypt_picc_data_aes`
  - `encrypt_sdm_file_data_aes`
  - `decrypt_sdm_file_data_aes`
  - `sdm_mac_aes`
- LRP:
  - `derive_sdm_keys_lrp`
  - `encrypt_picc_data_lrp`
  - `decrypt_picc_data_lrp`
  - `encrypt_sdm_file_data_lrp`
  - `decrypt_sdm_file_data_lrp`
  - `sdm_mac_lrp`

Useful supporting types:

- `SdmReadCtr([u8; 3])`
- `PiccDataTag`
- `MirroredMeta { uid: bool, read_ctr: bool }`
- `SdmAesKeys { enc: [u8; 16], mac: [u8; 16] }`
- `SdmLrpKeys { enc: Lrp, mac: Lrp }`

## Test Vectors

All vectors below are reproduced verbatim from NXP AN12196 rev. 2.0
(4 March 2025), sections `3.3` and `3.4`. They cover AES mode only
(AN12196 does not supply SDM vectors in LRP mode).

Hex is lower-case here; capital `h` suffixes from the source have been
dropped for clarity. Byte order follows the datasheet: `UID` is 7 bytes
MSB-first, `SDMReadCtr` is 3 bytes LSB-first in crypto inputs.

### SDMMAC — zero-length input (`§3.4.4.2.1`, `Table 4`)

`SDMMACInputOffset == SDMMACOffset`, so the CMAC is computed over the
empty string.

```text
SDMFileReadKey        = 00000000000000000000000000000000
SDMMetaReadKey        = 00000000000000000000000000000000
PICCEncData           = EF963FF7828658A599F3041510671E88

# Recover PICC metadata → same UID / counter as §3.4.2.2
UID                   = 04DE5F1EACC040
SDMReadCtr            = 3D0000

SV2                   = 3CC30001008004DE5F1EACC0403D0000
SesSDMFileReadMACKey  = CMAC(SDMFileReadKey; SV2)
                      = 3FB5F6E3A807A03D5E3570ACE393776F

# CMAC subkey derivation (NIST SP 800-38B)
L  = AES-ECB-ENC(SesSDMFileReadMACKey, 0^16)
   = 0E2F0C519F60EB99497EED68B3F7C5A5
K1 = L  << 1                    = 1C5E18A33EC1D73292FDDAD167EF8B4A
K2 = K1 << 1                    = 38BC31467D83AE6525FBB5A2CFDF1694
# (no xor with Rb needed here — MSB1(L) and MSB1(K1) are 0)

# MAC of the empty message M = ε
M1 = K2 ⊕ (80 || 0^15)          = B8BC31467D83AE6525FBB5A2CFDF1694
T  = AES-ECB-ENC(SesSDMFileReadMACKey, M1)
   = E194C7EE12D9F7EE8A65C8331B704386

SDMMAC = MACt = pick bytes 1,3,5,7,9,11,13,15 of T    (0-based)
             = 94EED9EE65337086
```
